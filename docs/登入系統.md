# 登入系統

隊員從 LINE 打開本站，用 LINE 帳號直接登入，不需另外註冊。登入後本站發一張 30 天有效的登入憑證（存在 cookie），之後 30 天內重開都不用再經過 LINE。

## 登入流程

`useMe().init()`，由 `AuthGate` 在進入需登入的頁面時呼叫，整個 app 只跑一次：

```
1. 打 GET /api/me
   ├─ 成功（cookie 有效）→ 登入完成，直接放行
   └─ 401（沒登入或憑證過期）→ 往下
2. 本機開發且開了測試登入？
   └─ 是 → 顯示「開發用測試登入」畫面（見下方），結束
3. LINE LIFF 登入
   ├─ liff.init({ liffId })
   ├─ 還沒登入 LINE（外部瀏覽器）→ liff.login() 導去 LINE 登入，回來後重跑
   ├─ 取 idToken；確定已過期 → 依環境恢復（見下方「idToken 過期」）
   └─ POST /api/auth/line { idToken }
        ├─ 成功 → 後端驗證、建立或更新帳號、發 cookie → 登入完成
        └─ 失敗 → 顯示「無法使用」畫面與原因（例：此帳號已被停用）
```

**為什麼先認自己的 cookie、不每次都驗 LINE**：LINE 的 idToken 壽命很短，而且 LINE 常把舊的頁面連同已過期的 token 一起還原。若每次開啟都硬驗 LINE，老用戶重開會被「IdToken expired」擋在門外。

### idToken 過期
| 環境 | 處理 |
|---|---|
| LINE 內建瀏覽器 | `liff.login()` 不會刷新 token（官方不支援），改顯示「登入資訊已過期，請關閉本頁後，從 LINE 選單重新開啟」 |
| 外部瀏覽器 | 自動重新登入一次。用 `sessionStorage` 記旗標，同一分頁已重登過還是過期就不再重試，避免無限迴圈 |

前端判斷「確定過期」時含 30 秒緩衝；解不出到期時間就不自己判斷，交給後端。

### 登入後一律導回首頁
`liff.login()` 預設回到當下網址；從 `/cancel` 等子頁登入時，網址會對不上 LINE Login channel 註冊的 Callback URL 而被擋，所以固定導回站台根網址（`loginRedirect()`）。

## 登入閘門（AuthGate）畫面判斷

依序判斷，符合第一個就顯示：

| 條件 | 顯示 |
|---|---|
| 頁面設了 `definePageMeta({ public: true })` | 直接顯示頁面，不跑登入（例：`/privacy`、`/ui-preview`） |
| `fatal` 有值 | 「無法使用」＋原因＋「請聯絡管理員」 |
| 載入中 | 「載入中…」 |
| 需要測試登入 | 開發用測試登入畫面 |
| 已登入但帳號停用中 | 重新啟用畫面（進來自動跳確認框） |
| 已登入 | 頁面內容＋首次設定彈窗（若還沒完成）；設定完成後若有請假場次異動，跳異動通知（見 [請假頁](請假頁.md#請假場次異動通知)） |

## 兩個名字

| 畫面上叫 | 資料庫欄位 | 怎麼來的 | 用途 |
|---|---|---|---|
| **名字** | `users.real_name` | 首次設定自己填，之後在個人頁可改；填名字或綽號都可以，**不強制真名** | 首頁、名單、統計、報表的主要顯示 |
| **LINE 名稱** | `users.display_name` | 每次登入從 LINE 自動同步，使用者不能在本站改 | 對照用（例：首頁「LINE 名稱：○○」、封存報表的「LINE名稱」欄） |

- 欄位名稱 `real_name` 是沿用 Next.js 版的歷史命名，內容不一定是真名。
- LINE 登入只拿得到「顯示名稱」，拿不到可用來搜尋加好友的「LINE ID」，所以第二個欄位叫「LINE 名稱」不叫「LINE ID」。
- 2026-10-02 用詞統一：原本兩個都叫「暱稱」容易混淆，自己填的改叫「名字」、LINE 帶入的改叫「LINE 名稱」；後端錯誤訊息也從「姓名」改成「名字」。隱私權政策與同意框只改用詞（「暱稱（綽號）」→「名字（可填綽號）」），內容意思不變（仍不強制蒐集真實姓名），**條款版本不升、不需要大家重新同意**。

## 首次設定三關

新帳號依序完成，前一關完成才跳下一關，彈窗不能關閉略過。判斷規則集中在 `shared/utils/setup.ts` 的 `setupStage()`：

| 關卡 | 什麼時候跳 | 完成後 |
|---|---|---|
| 1. 確認名字（`NameDialog`） | `real_name` 是空的 | 存 `real_name`。預填 LINE 名稱讓使用者確認或微調，1～20 字 |
| 2. 同意條款（`ConsentDialog`） | `terms_version` ≠ 現行版本 | 存現行版本。**條款升版**（改 `shared/utils/terms.ts`）後所有人下次進來都會再跳 |
| 3. 退費途徑（`RefundDialog`） | LINE PAY、銀行轉帳都沒勾 | 存退費途徑；選銀行必填代號（3～7 位數字）與帳號（5～20 位數字，可含空白或連字號） |

**與 Next.js 版差異**：原版只在首頁掛這三個彈窗，從其他頁直接開啟會略過；Nuxt 版由 `AuthGate` 掛在所有需登入的頁面，不論從哪頁進來都會先完成設定。

## 帳號停用的兩種情況

| 情況 | 登入時 | 之後 |
|---|---|---|
| 自己停用（`self_deactivated = true`） | 可以登入；`GET /api/me` 也照常回資料（`isActive: false`） | 直接顯示停用畫面，可自己重新啟用（下一季起回到季報，非當季） |
| 管理員停用 | `POST /api/auth/line` 回 403「此帳號已被停用」；`GET /api/me` 回 401 | 只能請管理員啟用 |

「誰能進本站」的規則只寫在一個地方：`server/utils/me.ts` 的 `canSignIn()`（啟用中，或自己停用），LINE 登入與 `GET /api/me` 共用。
停用中的人除了讀自己資料、重新啟用之外，其他 API 一律用 `currentUser()`，回 401，什麼都不能操作。

**與 Next.js 版差異**：原版 `GET /api/me` 對自己停用的人回 401，他每次打開都得重走 LINE 登入才看得到重新啟用畫面；遇到 LINE 還原過期的登入資訊，就會卡在「登入資訊已過期」按不到重新啟用。Nuxt 版直接認 30 天登入憑證。

### 季報期間怎麼變（實測紀錄）
自己停用與重新啟用都是「下一季起」生效，資料庫的在隊期間（`membership_periods`）會長這樣（例：10/2 停用、同季又重新啟用）：

| 開始 | 結束 | 說明 |
|---|---|---|
| 2026-10-02 | 2027-01-01 | 停用：結束日設為下一季首日，本季照算 |
| 2027-01-01 | （空白＝仍在隊） | 重新啟用：從下一季首日開始算 |

## 登入憑證（session）

| 項目 | 設定 |
|---|---|
| 格式 | JWT，HS256 簽章，內容 `{ app_user_id, app_role }` |
| 金鑰 | `NUXT_SESSION_SECRET`（至少 32 字元，太短直接拒絕簽發） |
| 有效期 | 30 天 |
| cookie 名稱 | `leave_session` |
| cookie 屬性 | `HttpOnly`（前端 JS 讀不到）、`SameSite=Lax`、正式環境 `Secure`（只走 https）、`Path=/` |

**每次請求都回資料庫確認角色與停用狀態**（`currentUser()`），不相信憑證裡的角色。否則憑證有效 30 天內會有三個漏洞：被停用的人還能操作、被降級的管理員還進得去後台、剛升級的人要等 30 天才生效。

**與 Next.js 版差異**：原版借用 Supabase 的 JWT secret 簽憑證；Nuxt 版改用自己的 `NUXT_SESSION_SECRET`。因為前端從不直接連資料庫，這張憑證只在本程式內部使用，不需要跟 Supabase 綁在一起。

## 開發用測試登入

LINE LIFF 只接受 https 網址，本機 `localhost` 無法走 LINE 登入，所以本機開發改用測試帳號：

| 測試帳號 | 角色 | 資料庫的 `line_user_id` |
|---|---|---|
| 測試成員 | member | `dev-member` |
| 測試二級管理員 | admin2 | `dev-admin2` |
| 測試一級管理員 | admin1 | `dev-admin1` |

- 登入後右上角有「開發：切換帳號」，可換角色測試。
- 測試帳號的 `line_user_id` 以 `dev-` 開頭，不會跟真實 LINE 使用者（`U` 開頭）衝突。

**安全：正式環境一定打不開**，兩道鎖缺一不可：
1. `import.meta.dev`：Nuxt 正式建置時固定為 `false`，測試登入的程式在正式版產物裡根本不存在（已確認建置產物不含測試帳號字串）。
2. `NUXT_DEV_LOGIN=1`：本機也要明確打開。

實測：正式版伺服器就算設了 `NUXT_DEV_LOGIN=1`，`POST /api/auth/dev-login` 仍回 **404**。

## API

所有回應為 JSON；錯誤一律 `{ error: '訊息' }`。需登入的 API 沒有有效登入時回 401「未登入」。

### `POST /api/auth/line` — LINE 登入
| | |
|---|---|
| body | `{ idToken: string }`（LIFF 取得） |
| 流程 | 向 LINE 驗證 idToken（並比對 `aud` 是本站 channel，防止別的 LINE 應用的 token 混用）→ 依 `line_user_id` 建立或更新帳號（每次登入覆寫 LINE 名稱與大頭貼、更新最後登入時間）→ 發 cookie |
| 成功 | `{ user: Me, needsName: boolean }` |
| 400 | 缺少 idToken |
| 401 | LINE 驗證失敗（例：`IdToken expired.`、audience 不符） |
| 403 | 此帳號已被停用（管理員停用） |
| 500 | 建立帳號失敗 |

### `POST /api/auth/dev-login` — 測試登入（只有本機開發）
| | |
|---|---|
| body | `{ role: 'member' \| 'admin2' \| 'admin1' }` |
| 成功 | `{ ok: true }`＋cookie |
| 400 | role 不正確 |
| 404 | 正式環境，或沒開 `NUXT_DEV_LOGIN` |

### `POST /api/auth/logout` — 登出本站
清除 cookie，回 `{ ok: true }`。不會登出 LINE。Next.js 版沒有這支，Nuxt 版本機切換測試帳號會用到。

### `GET /api/me` — 目前登入者
回 `Me`：`{ id, displayName, pictureUrl, realName, role, isActive, termsVersion, refundLinePay, refundBank, bankCode, bankAccount }`。
自己停用的人也回資料（`isActive: false`），畫面據此顯示重新啟用；沒登入或被管理員停用回 401。

### `PATCH /api/me` — 修改名字
| | |
|---|---|
| body | `{ realName: string }`（去頭尾空白後 1～20 字） |
| 成功 | 更新後的 `Me` |
| 400 | 「名字不可空白」、「名字請控制在 20 字以內」 |

### `PATCH /api/me/terms` — 同意現行條款
不需 body，回 `{ ok: true, version }`。

### `PATCH /api/me/refund` — 儲存退費途徑
| | |
|---|---|
| body | `{ refundLinePay: boolean, refundBank: boolean, bankCode?: string, bankAccount?: string }` |
| 規則 | 至少選一種；選銀行時代號 3～7 位數字、帳號 5～20 位數字（先去空白與連字號）。沒選銀行時清空代號與帳號 |
| 成功 | `{ ok: true }` |
| 400 | 都沒選、格式錯誤（訊息與前端一致，同一份 `shared/utils/banks.ts`） |

### `PATCH /api/me/active` — 自助停用／重新啟用
| | |
|---|---|
| body | `{ active: boolean }` |
| 重新啟用 | 只有自助停用者可用：已啟用回 409、管理員停用回 403。呼叫資料庫 `reactivate_self` |
| 停用 | 已停用回 409；最後一位一級管理員不能停用自己（409）。呼叫資料庫 `deactivate_self` |

這支用 `sessionUser()`（不擋停用者），否則自助停用的人連重新啟用都進不來。停用的畫面入口在第 6 步「個人」頁。
